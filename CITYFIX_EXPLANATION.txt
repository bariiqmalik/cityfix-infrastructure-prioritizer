1. REAL-WORLD PROBLEMS IDENTIFIED (WHAT PEOPLE WE FOUND / PAIN POINTS)
================================================================================

Through research into civic operations and municipal infrastructure maintenance 
in high-density urban environments (such as Indian and global metropolitan areas),
we identified three distinct stakeholder groups suffering from critical friction:

A. Everyday Citizens & Commuters:
   - Severe Safety Hazards: Deep potholes, displaced manhole covers, exposed
     cables from damaged streetlights, and storm drain waterlogging cause fatal
     accidents, vehicular damage, and pedestrian injuries.
   - Complaint Black Hole ("File and Forget"): Citizens submit complaints through
     clunky municipal grievance forms or phone helplines, but receive zero 
     visibility into status, priority, or dispatch timelines.
   - Inconvenient Location Reporting: Traditional forms require typing complex
     postal addresses rather than tapping a live map pin or using smartphone GPS.

B. Municipal Dispatchers & Public Works Departments (PWD):
   - Complaint Fatigue & Volume Overload: Thousands of complaints arrive daily 
     across roads, lighting, sanitation, and drainage. Dispatchers lack an 
     automated, objective mechanism to decide which crew goes where first.
   - Inefficiency of First-Come, First-Served (FIFO) Queues:
     Under conventional FIFO, a cosmetic complaint filed at 8:00 AM (e.g., minor 
     graffiti on a curb) is placed ahead of a life-threatening emergency reported 
     at 9:00 AM (e.g., collapsed asphalt on a major arterial highway).
   - "Squeaky Wheel" Bias: Politically vocal citizens or repeat callers get issues 
     resolved faster, while quieter or lower-income neighborhoods are neglected.

C. City Administrators & Ward Councillors:
   - Starvation of Backlog Issues: Minor issues in low-traffic alleys sit in 
     databases for years without being fixed because new high-priority reports 
     keep taking precedence.
   - Commercial Map Licensing Costs: Traditional platforms rely on commercial map
     APIs (e.g., Google Maps) that require expensive monthly API billing, quota 
     limits, and billing cards, which public municipal budgets often cannot sustain.

2. THE SOLUTION WE OFFERED (CITYFIX ARCHITECTURE & USER WORKFLOW)
================================================================================

We designed and implemented "CityFix" - an intelligent, data-driven municipal
infrastructure management platform that replaces manual discretion with an 
algorithmic, mathematically rigorous Binary Max-Heap prioritization engine.

Key Modules of the Solution:

1. Citizen Issue Submission Portal (`submit.html`):
   - Zero-Friction Reporting: Allows citizens to select the issue category (Road 
     Damage, Broken Streetlight, Water Logging, Traffic Signal, Sidewalk Hazard).
   - 100% Free Open-Source Map with India Focus: Uses Leaflet integrated with
     free OpenStreetMap (OSM) tiles—no proprietary API keys or billing required.
   - Drag-and-Drop Pinpoint & "My Current GPS": Citizens can tap anywhere on the 
     map of India or click "My Current GPS" to auto-populate exact latitude and 
     longitude coordinates. Quick-jump presets for Delhi NCR, Mumbai, Bengaluru, 
     Kolkata, and Chennai enable instant panning.
   - Live Algorithmic Urgency Preview: Dynamically computes and displays the 
     projected urgency score in real-time as the citizen adjusts severity and 
     traffic sliders.

2. Custom Binary Max-Heap Algorithmic Engine (`CustomMaxHeap.java`):
   - A from-scratch, pure array-based priority queue strictly avoiding Java's 
     built-in `java.util.PriorityQueue` to maintain absolute control over memory,
     dynamic capacity scaling, and custom heap invariants.
   - Evaluates every repair request dynamically using the Urgency Formula:
     Urgency = (Severity * 0.5) + (Traffic Impact * 0.3) + (Report Count * 0.2)
               + Time-Elapsed Starvation Penalty

3. Municipal Executive Dashboard (`index.html`):
   - Real-Time KPIs: Total active reports, critical priority count, active field 
     crews, and average resolution turnaround.
   - Dynamic Geographic Heat Map: Interactive Leaflet map displaying colored pins 
     (Red = High Urgency >=80, Amber = Medium 60-79, Green = Low <60).
   - Live Max-Heap Dispatch Queue: Always surfaces the top issues extracted from 
     the Max-Heap root, ready for instant one-click crew dispatch (`extractMax()`).

4. Crew Task Management & Audit Log (`tasks.html` & `reports.html`):
   - Multi-facet search and filtering by status (`pending`, `in-progress`, `resolved`),
     priority level, and issue category.
   - Complete historical ledger linked with SQL database records for accountability.

4. WHY WE USE JAVA (ENGINEERING RATIONALE & SYSTEM STABILITY)
================================================================================

Java was chosen as the core enterprise backend language for critical reasons:

1. Strict Compile-Time Type Safety & Data Integrity:
   Municipal software handles public safety data. Java's strong typing guarantees
   that coordinates, severity ratings (1-10), and timestamps are rigorously validated
   before reaching storage or memory.

2. Predictable Memory Management for Data Structures:
   Implementing a custom binary heap requires low-level control over contiguous
   array allocations. Java provides garbage-collected memory safety while retaining
   deterministic O(1) array index addressing (`heap[i]`), avoiding pointer bugs or
   memory leaks prevalent in lower-level languages.

3. Native Thread Synchronization & Concurrency:
   When hundreds of citizens submit reports simultaneously and municipal dispatchers
   call `extractMax()`, Java's built-in `synchronized` concurrency controls and 
   atomic thread primitives protect the heap and database connection pool from race 
   conditions and corrupted tree states.

4. Zero-Dependency Standalone Server Capability:
   Using Java SE's built-in `com.sun.net.httpserver`, CityFix runs as a lightweight,
   high-performance standalone web server with ZERO heavy third-party web frameworks
   (pure Java 17+ SE). It can be deployed on any low-spec municipal server or VM.

5. Enterprise JDBC & Relational DBMS Standards:
   Java's JDBC API provides standardized, robust communication with relational 
   databases (PostgreSQL, MySQL, H2) using prepared statements, transaction 
   isolation, and connection pooling.

Below are the key Java classes and functions used:

--------------------------------------------------------------------------------
A. Class: `com.cityfix.heap.CustomMaxHeap`
--------------------------------------------------------------------------------
This class implements a complete binary max-heap stored in a contiguous array:
- Parent of index `i` is located at `(i - 1) / 2`
- Left child is at `2 * i + 1`
- Right child is at `2 * i + 2`

Key Functions Implemented:

1. `void insert(RepairTask task)`
   - Purpose: Inserts a newly reported infrastructure issue into the heap.
   - How it works:
     a) Verifies capacity; if internal array is full, calls `ensureCapacity()` 
        which doubles array size using `Arrays.copyOf()`.
     b) Places the task at index `size` (the next open position in the complete tree).
     c) Increments `size`.
     d) Calls `heapifyUp(size - 1)` to bubble the task upward into its correct place.
   - Time Complexity: O(log N).

2. `void heapifyUp(int index)`
   - Purpose: Restores the Max-Heap invariant from a given child index upwards.
   - How it works:
     Iteratively compares `calculateUrgencyScore()` of the current node with its
     parent. If current urgency > parent urgency, it swaps their positions using 
     `swap(index, parentIndex)` and continues upward until the root or an ancestor
     with greater/equal urgency is reached.
   - Time Complexity: O(log N).

3. `RepairTask extractMax()`
   - Purpose: Dispatches the single highest-priority infrastructure repair task.
   - How it works:
     a) Checks if heap is empty; throws `NoSuchElementException` if size == 0.
     b) Captures root element `heap[0]` (the maximum urgency task).
     c) Replaces root `heap[0]` with the last element `heap[size - 1]`.
     d) Nullifies the last slot to aid Garbage Collection and decrements `size`.
     e) Calls `heapifyDown(0)` to sink the new root to its appropriate position.
     f) Returns the extracted max task.
   - Time Complexity: O(log N).

4. `void heapifyDown(int index)`
   - Purpose: Restores the Max-Heap invariant downwards from the root.
   - How it works:
     Compares the node at `index` with its left and right children. Identifies the
     largest urgency score among the three. If a child has a higher urgency score 
     than the parent, swaps the parent with that largest child and recurses 
     downwards until the heap invariant is fully satisfied.
   - Time Complexity: O(log N).

5. `RepairTask peekMax()`
   - Purpose: Inspects the highest-priority task without removing it.
   - How it works: Returns `heap[0]` directly.
   - Time Complexity: O(1).

6. `CustomMaxHeap(List<RepairTask> tasks)` (Floyd's Heap Construction)
   - Purpose: Builds a valid heap from an existing list of database records.
   - How it works: Copies records into the internal array and executes downward
     heapification (`heapifyDown`) starting from the last non-leaf node:
     `for (int i = (size - 1) / 2; i >= 0; i--) heapifyDown(i);`
   - Time Complexity: O(N) linear time (significantly faster than N * log N inserts).

7. `List<RepairTask> extractAllSorted()`
   - Purpose: Produces an audit-ready, strictly descending prioritized list for 
     the dashboard without destroying the original heap state.
   - How it works: Creates an isolated temporary clone of the heap and repeatedly 
     executes `extractMax()` until empty.
   - Time Complexity: O(N log N).

B. Class: `com.cityfix.model.RepairTask`
--------------------------------------------------------------------------------
Represents the municipal incident entity and encapsulates the scoring algorithm.

Key Functions Implemented:

1. `double calculateUrgencyScore()`
   - Mathematical Formula:
     Score = (Severity * 0.5) + (TrafficVolume * 0.3) + (ReportCount * 0.2)
             + TimeElapsedPenalty
   - Input Clamping:
     `int clampedSeverity = Math.max(1, Math.min(10, severity));`
     `int clampedTraffic  = Math.max(1, Math.min(10, trafficVolume));`
     `int clampedReports  = Math.max(1, reportCount);`
   - Anti-Starvation Elapsed Time Penalty:
     Calculates elapsed hours using `Duration.between(timestamp, Instant.now())`.
     Adds 0.05 penalty points per elapsed hour, capped at 2.0 points:
     `double timeElapsedPenalty = Math.min(2.0, hoursElapsed * 0.05);`

2. `int getDisplayScore()`
   - Normalizes raw urgency score to an intuitive integer scale between 10 and 100:
     `int score = (int) Math.round(calculateUrgencyScore() * 10.0);`
     `return Math.max(10, Math.min(100, score));`

3. `String getPriorityLevel()`
   - Maps scores to UI pill categories:
     * Score >= 80 -> "High" (Red)
     * Score 60-79 -> "Medium" (Amber)
     * Score < 60  -> "Low" (Green)

4. `int compareTo(RepairTask other)`
   - Implements Java's `Comparable<RepairTask>` interface:
     `return Double.compare(this.calculateUrgencyScore(), other.calculateUrgencyScore());`

6. DATABASE MANAGEMENT SYSTEM (DBMS ARCHITECTURE, SCHEMA & INDEXING)
================================================================================

CityFix utilizes a Relational Database Management System (compatible with 
PostgreSQL, MySQL, and H2) defined in `schema.sql`.

--------------------------------------------------------------------------------
A. Relational Table Schema
--------------------------------------------------------------------------------

1. Table: `users`
   Stores registered citizens, inspectors, and municipal administrators.

   CREATE TABLE users (
       user_id SERIAL PRIMARY KEY,
       name VARCHAR(100) NOT NULL,
       role VARCHAR(20) NOT NULL CHECK (role IN ('citizen', 'admin')),
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   );

2. Table: `reports`
   Stores the core incident records and spatial metadata.

   CREATE TABLE reports (
       report_id SERIAL PRIMARY KEY,
       task_code VARCHAR(20) UNIQUE,
       user_id INT REFERENCES users(user_id) ON DELETE SET NULL,
       issue_type VARCHAR(100) NOT NULL,
       location_name VARCHAR(255) NOT NULL,
       description TEXT,
       latitude DECIMAL(10, 6) NOT NULL,
       longitude DECIMAL(10, 6) NOT NULL,
       severity_rating INT NOT NULL CHECK (severity_rating BETWEEN 1 AND 10),
       traffic_impact INT NOT NULL CHECK (traffic_impact BETWEEN 1 AND 10),
       report_count INT NOT NULL DEFAULT 1 CHECK (report_count >= 1),
       status VARCHAR(20) NOT NULL DEFAULT 'pending' 
              CHECK (status IN ('pending', 'in-progress', 'resolved')),
       created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
       updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
   );

--------------------------------------------------------------------------------
B. DBMS Constraints & Data Integrity Safeguards
--------------------------------------------------------------------------------
1. Primary Keys (`report_id`, `user_id`): Guarantees entity uniqueness.
2. Foreign Key (`user_id REFERENCES users`): Enforces referential integrity with
   `ON DELETE SET NULL` so reports remain preserved even if a user account is deleted.
3. Domain `CHECK` Constraints:
   - `severity_rating BETWEEN 1 AND 10`: Prevents invalid severity entries at the 
     database engine level.
   - `traffic_impact BETWEEN 1 AND 10`: Restricts traffic metrics to valid range.
   - `status IN ('pending', 'in-progress', 'resolved')`: Enforces the municipal 
     state machine workflow.
4. Precision Coordinates (`DECIMAL(10, 6)`):
   Storing latitude and longitude as 6-decimal fixed-point numbers preserves 
   accuracy down to ~0.11 meters (11 centimeters) on the Earth's surface—crucial 
   for distinguishing adjacent utility poles, culverts, or lanes.

--------------------------------------------------------------------------------
C. Indexing Strategy for Accelerated Municipal Queries
--------------------------------------------------------------------------------
High-volume city databases experience heavy read and filter loads. We implemented
four dedicated B-Tree indexes:

1. `CREATE INDEX idx_reports_status ON reports(status);`
   - Accelerates fetching only actionable tasks (`status = 'pending' OR 'in-progress'`)
     when rebuilding the in-memory Max-Heap. Avoids full-table scans.

2. `CREATE INDEX idx_reports_issue_type ON reports(issue_type);`
   - Speeds up departmental category breakdown queries (e.g. Roads vs. Electrical).

3. `CREATE INDEX idx_reports_created_at ON reports(created_at DESC);`
   - Optimizes time-series analytics and the "Recent Reports" dashboard table.

4. `CREATE INDEX idx_reports_severity_traffic ON reports(severity_rating, traffic_impact);`
   - Composite index allowing composite range filtering across severity and traffic.

--------------------------------------------------------------------------------
D. Java JDBC Implementation (`ReportDAOImpl.java`)
--------------------------------------------------------------------------------
- Uses `java.sql.PreparedStatement` for all DML operations (INSERT, UPDATE, SELECT)

7. DUAL-TIER DESIGN: IN-MEMORY MAX-HEAP + PERSISTENT RELATIONAL DBMS
================================================================================

A common system design question: "If we have a DBMS, why do we need a Max-Heap?
And if we have a Max-Heap, why do we need a DBMS?"

CityFix employs a specialized Dual-Tier Architecture to achieve the optimal 
balance of speed and durability:

   [ Citizen Form / Admin UI ]
              │
              ├───► REST API / Java Controller
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
   [ Relational DBMS ]            [ CustomMaxHeap ]
   • Permanent Storage (Disk)     • Active Working Set (RAM)
   • ACID Transactions            • Instant O(1) peekMax()
   • Complex Historical Queries   • Fast O(log N) Priority Dispatch
   • Audit & Compliance           • Live Dynamic Urgency Scoring

1. Why DBMS alone is insufficient for real-time dispatch:
   Computing dynamic priority in pure SQL requires evaluating dynamic time penalties:
   `ORDER BY (severity*0.5 + traffic*0.3 + report_count*0.2 + LEAST(2.0, EXTRACT(EPOCH FROM ...))) DESC`
   On a database with tens of thousands of rows, running this calculation on disk 
   for every dispatcher request causes high CPU usage, lock contention, and disk I/O.

2. Why Max-Heap alone is insufficient:
   In-memory data structures are volatile. If a server restarts or crashes, all 
   reported incidents would be lost.

3. The Dual-Tier Solution:
   - When a report arrives, it is permanently written to SQL (ACID durability).
   - Concurrently, it is placed in the RAM-based `CustomMaxHeap` for instant O(1) 
     inspection and O(log N) prioritized extraction.
   - When the server boots up, `PrioritizerService.rebuildHeapFromDatabase()` uses 
     Floyd's algorithm to reconstruct the entire Max-Heap from the database in O(N).
